Orientation

What you are actually building

One S3 bucket holds everything. There is no database — that was designed out, because a Vercel function has no fixed IP address to allowlist against RDS, and the bucket already answers every question the tables would have. Two prefixes, two very different lifetimes:

PrefixHoldsWritten byCache-Control
stories/<id>.json A published exhibit POST /api/publish max-age=60, must-revalidate — changes when republished
assets/<sha256>/full.webp One uploaded image The browser, via a signed URL max-age=31536000, immutable — can never change
tmp/ Scratch. Nothing important. Nothing yet The only thing safe to auto-delete

An image's filename is the fingerprint of its own bytes. That's what makes uploads idempotent and safe to leave public: the same photo uploaded twice lands on the same key, and nobody can claim a key for content that doesn't hash to it.

The upload path — note who talks to whom

Browserhashes the image, asks→POST /api/story-assets
Functionchecks S3, returns a→signed upload URL+ 3 required headers
Browser→PUT direct to S3(not through Vercel)
Viewer→GET direct from S3then inlines the bytes into the artwork
Why this matters for Step 2

The browser uploads to S3 directly and the viewer reads from S3 directly. Vercel is never in the middle of the bytes. So the bucket's own CORS rules are what make or break both paths — this is the single most common way this setup fails.

STEP 0

Get a working AWS CLI

You need credentials before you can create the credentials. One-time console visit.

Install the CLI:

PowerShell
winget install -e --id Amazon.AWSCLI

Open a new terminal afterwards so the PATH refreshes, then confirm:

PowerShell
aws --version

Now get an access key for yourself in the AWS console: IAM → Users → your user → Security credentials → Create access key, choosing Command Line Interface. Then:

PowerShell
aws configure

Paste the key and secret, set the region to {{REGION}}, leave output format blank. Verify you are who you think you are:

PowerShell
aws sts get-caller-identity
Trap

The Account field in that output is your AWS account ID. Copy it into the values panel at the top of this page now — Step 5 needs it and an incorrect one produces a role that silently never works.

STEP 1

Create the bucket

One bucket holds published exhibits and every uploaded image.

Trap — region syntax

us-east-1 is the one region that must omit --create-bucket-configuration. Every other region requires it. Use whichever of the two commands matches your region.

If region IS us-east-1
aws s3api create-bucket --bucket {{BUCKET}} --region us-east-1
If region is anything else
aws s3api create-bucket --bucket {{BUCKET}} --region {{REGION}} \
  --create-bucket-configuration LocationConstraint={{REGION}}

Next, allow a bucket policy to grant public reads while keeping public ACLs blocked. Published exhibits have to be world-readable; ACLs are a legacy mechanism you never want on:

PowerShell
aws s3api put-public-access-block --bucket {{BUCKET}} `
  --public-access-block-configuration "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=false,RestrictPublicBuckets=false"
STEP 2

CORS — the load-bearing one

Both the upload and the display go browser-to-S3 directly. Get this wrong and images vanish without an error.

Save this as cors.json:

cors.json
{
  "CORSRules": [
    {
      "AllowedOrigins": ["{{APP_ORIGIN}}"],
      "AllowedMethods": ["GET", "HEAD", "PUT"],
      "AllowedHeaders": ["content-type", "if-none-match", "x-amz-checksum-sha256"],
      "ExposeHeaders": ["ETag"],
      "MaxAgeSeconds": 3000
    }
  ]
}
PowerShell
aws s3api put-bucket-cors --bucket {{BUCKET}} --cors-configuration file://cors.json
Trap — those three headers are not optional

if-none-match and x-amz-checksum-sha256 are part of the upload's cryptographic signature. The browser must send them and S3 must be willing to receive them. Drop either from AllowedHeaders and every upload fails the CORS preflight — before the request is even attempted.

Trap — preview deployments

Vercel generates a new URL for every preview deployment, so preview origins cannot be listed here in advance. Images will be blank on preview URLs and correct in production. That is expected, not a bug — decide now that you know it, rather than debugging it later. Attach a stable custom domain if you need previews to work.

STEP 3

Lifecycle rule — scoped to scratch only

The rule that deletes things. It must never point at anything real.

Why this step exists

The Terraform written for the earlier testbed expires the whole bucket after 90 days. That was harmless when the bucket held disposable test uploads. Applied to this bucket it would delete every published exhibit's images three months after upload — silently, and long after anyone would connect the two events. Never apply that file as written.

Save as lifecycle.json:

lifecycle.json
{
  "Rules": [
    {
      "ID": "expire-scratch-only",
      "Status": "Enabled",
      "Filter": { "Prefix": "tmp/" },
      "Expiration": { "Days": 90 }
    },
    {
      "ID": "abort-incomplete-uploads",
      "Status": "Enabled",
      "Filter": { "Prefix": "" },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 1 }
    }
  ]
}
PowerShell
aws s3api put-bucket-lifecycle-configuration --bucket {{BUCKET}} `
  --lifecycle-configuration file://lifecycle.json

Read it back and confirm the expiry rule says tmp/ and nothing else:

PowerShell
aws s3api get-bucket-lifecycle-configuration --bucket {{BUCKET}}
STEP 4

Make published content readable

Two prefixes public. Everything else stays private.

Save as bucket-policy.json:

bucket-policy.json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadPublishedContent",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": [
        "arn:aws:s3:::{{BUCKET}}/assets/*",
        "arn:aws:s3:::{{BUCKET}}/stories/*"
      ]
    }
  ]
}
PowerShell
aws s3api put-bucket-policy --bucket {{BUCKET}} --policy file://bucket-policy.json
This is intended, not a leak

A published exhibit is a public web page — its artwork has to be fetchable by any visitor's phone. Note what is not listed: tmp/ is private, and nobody can list the bucket's contents, so keys can't be enumerated.

STEP 5

Let Vercel write to the bucket

Two routes. Take A to get running today; B is the one worth ending up on.

Both routes use the same permission set. Save it as s3-write.json first:

s3-write.json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject"],
      "Resource": [
        "arn:aws:s3:::{{BUCKET}}/assets/*",
        "arn:aws:s3:::{{BUCKET}}/stories/*"
      ]
    }
  ]
}

s3:GetObject is there because the deduplication check uses HeadObject, which AWS authorises as a read.

Route A — access keys (fastest)

PowerShell
aws iam create-user --user-name arcade-publisher

aws iam put-user-policy --user-name arcade-publisher `
  --policy-name arcade-s3-write --policy-document file://s3-write.json

aws iam create-access-key --user-name arcade-publisher

Keep the printed AccessKeyId and SecretAccessKey — the secret is shown once. They become AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY in Step 6.

Route B — Vercel OIDC (no stored secret)

Vercel proves its identity per request and AWS hands back credentials that expire in minutes. Nothing long-lived is stored anywhere. The code already supports this — it switches automatically when AWS_ROLE_ARN is set.

Check first — issuer mode

In Vercel: Team Settings → Security → OIDC Federation. If the issuer mode is Global, the URL below is https://oidc.vercel.com with no team slug, and the condition keys lose their slug too. The commands here assume Team mode.

PowerShell
aws iam create-open-id-connect-provider `
  --url https://oidc.vercel.com/{{TEAM_SLUG}} `
  --client-id-list https://vercel.com/{{TEAM_SLUG}}

Save as trust.json:

trust.json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::{{ACCOUNT_ID}}:oidc-provider/oidc.vercel.com/{{TEAM_SLUG}}"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "oidc.vercel.com/{{TEAM_SLUG}}:aud": "https://vercel.com/{{TEAM_SLUG}}"
        },
        "StringLike": {
          "oidc.vercel.com/{{TEAM_SLUG}}:sub": "owner:{{TEAM_SLUG}}:project:{{PROJECT}}:environment:*"
        }
      }
    }
  ]
}
Trap — do not copy the audience from Vercel's docs

Vercel's own S3 example passes audience: 'sts.amazonaws.com' and shows a trust policy to match. This project's code does not pass an audience — api/_s3.ts calls awsCredentialsProvider({ roleArn }) and nothing else, so the token arrives with the default audience https://vercel.com/{{TEAM_SLUG}}.

Use sts.amazonaws.com here and every publish fails with “Not authorized to perform sts:AssumeRoleWithWebIdentity” — a message that points at permissions rather than at the audience mismatch actually causing it.

PowerShell
aws iam create-role --role-name arcade-vercel `
  --assume-role-policy-document file://trust.json

aws iam put-role-policy --role-name arcade-vercel `
  --policy-name arcade-s3-write --policy-document file://s3-write.json

aws iam get-role --role-name arcade-vercel --query Role.Arn --output text

That last command prints the ARN you'll paste as AWS_ROLE_ARN.

Trap — VITE_ values are baked in at build time

They are compiled into the JavaScript bundle, not read at runtime. Setting or changing one has no effect until you redeploy. Editing a value and refreshing the page will convince you the variable is broken when it simply hasn't been rebuilt.

The same fact is a security rule: anything named VITE_* is visible to anyone who opens the bundle. Never put a secret behind that prefix.

Also worth knowing

Vercel sets a built-in AWS_REGION that changes with the function's execution region. This project deliberately reads S3_REGION instead, so that instability can't misroute your calls. Don't "tidy" it into AWS_REGION.

STEP 7

Verify

Four checks, cheapest first. Each one fails differently, so do them in order.

1 — The CORS preflight, exactly as the browser sends it

Git Bash
curl -s -o /dev/null -D - -X OPTIONS \
  "https://{{BUCKET}}.s3.{{REGION}}.amazonaws.com/assets/probe/full.webp" \
  -H "Origin: {{APP_ORIGIN}}" \
  -H "Access-Control-Request-Method: PUT" \
  -H "Access-Control-Request-Headers: content-type,if-none-match,x-amz-checksum-sha256"
Pass

200, with Access-Control-Allow-Origin echoing your origin and all three request headers listed in Access-Control-Allow-Headers. A 403 means Step 2's header list is incomplete.

2 — Publish a real exhibit

Open the studio, make any small edit, publish. Then confirm the object landed:

PowerShell
aws s3 ls s3://{{BUCKET}}/stories/
aws s3 ls s3://{{BUCKET}}/assets/

3 — Confirm the cache headers survived the write

Substitute the story id you just published:

Git Bash
curl -sI "https://{{BUCKET}}.s3.{{REGION}}.amazonaws.com/stories/YOUR-STORY-ID.json" \
  | grep -i "http/\|cache-control"
Pass

200 and cache-control: public, max-age=60, must-revalidate. A longer max-age on stories/ means republishing stays invisible to visitors until the cache expires. Assets should read immutable instead — that difference is deliberate.

4 — A real phone

Open the published link on a phone and check that an uploaded image actually appears in the scene. This is the only test that exercises the whole chain, and the only one that can catch the remaining unknown: how large a data: URL a given phone will accept before it gives up. A blank rectangle where a photo should be means the bytes never arrived — start at the browser console, then Step 2.

OPTIONAL

CloudFront, later

Skip until the S3-direct setup is proven working. It adds speed and one nasty failure mode.

Serving straight from S3 works and costs almost nothing at exhibit scale. A CDN buys lower latency for distant visitors and cheaper egress at volume. Add it only when you want those, and only after Step 7 passes — otherwise a CDN problem and a bucket problem look identical.

The trap that makes this worth postponing

CloudFront caches responses. If Origin is not part of the cache key, the first request that arrives without an Origin header caches a response carrying no CORS headers — and that cached copy is then served to real browsers, which reject it.

The symptom is the worst kind: it depends on cache state. It passes when you test it and fails for a visitor an hour later, in a region you didn't test from.

Three settings, all required together:

SettingValue
OriginThe S3 bucket, via Origin Access Control
Cache policyMust include Origin in the cache key
Origin request policyManaged CORS-S3Origin, so Origin reaches the bucket at all

Test it on a cold cache, in this exact order — testing only the warm path hides precisely this defect:

Git Bash
# 1. Prime the cache deliberately WITHOUT an Origin header.
curl -sI "https://YOUR-CDN-DOMAIN/assets/SOME-SHA/full.webp" \
  | grep -i "access-control\|x-cache"

# 2. Now ask again the way a browser would.
curl -sI -H "Origin: {{APP_ORIGIN}}" \
  "https://YOUR-CDN-DOMAIN/assets/SOME-SHA/full.webp" \
  | grep -i "access-control-allow-origin\|x-cache"

Step 2 must return access-control-allow-origin. If it doesn't, Origin is missing from the cache key. Once it passes, repoint VITE_ASSET_BASE_URL and VITE_STORY_BASE_URL at the CDN domain and redeploy.

What this costs to run

At exhibit scale this rounds to nothing. Storage is about 2.3¢ per GB per month; a hundred exhibits with images is comfortably under a gigabyte. Requests are fractions of a cent per thousand. Egress from S3 is the only line that grows with visitors, at roughly 9¢ per GB — and the first 100 GB each month is free.

The thing to actually watch: do not create the RDS Postgres instance from the older Terraform. It is around $15/month for a database this design deliberately does not use, and it cannot be reached from a Vercel function anyway. Set a billing alarm at $5 and you'll hear about anything unexpected long before it matters.

Things not to do

Don't apply infra/terraform/ as it stands. It expires the whole bucket after 90 days, creates the unused database, provisions a static-key IAM user, and defaults CORS to *. It was written for a different, disposable purpose.

Don't rename a stored object. An asset's key is the fingerprint of its own bytes; renaming breaks every exhibit referencing it, and re-uploading cannot repair it.

Don't widen the upload allowlist to non-WebP types. The read path fetches full.webp specifically. Anything stored under another extension is written to a key nothing ever reads — a permanent silent gap.

Don't put a secret behind VITE_. It ends up in the public bundle. This has already happened once in this project's history.
